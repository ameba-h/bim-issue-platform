# 数据库设计

> 表结构的真源是 `server/database/schema.ts`（SQLite），本页是带中文说明的速览与「为什么这么设计」。与代码对不上时**以代码为准并回头改本页**。库的实况以库为准，任何文档记载的条数都只是快照。

## 🗄️ 总览（14 张表）

| # | 表 | 中文 | 一句话用途 |
|---|---|---|---|
| 1 | `users` | 用户表 | 人和 AI 都在这张表里，靠主体类型区分 |
| 2 | `projects` | 项目表 | 项目的名片：名称 / 编号 / 封面 / 状态 + 问题取号器 + 项目设置 |
| 3 | `project_members` | 项目成员表 | 某人在某项目里担任什么角色 |
| 4 | `tags` | 分类类目表 | 四维度分类，每项目独立一套 41 项标准 |
| 5 | `issues` | 问题表 | **核心表**，一条问题一行 |
| 6 | `issue_tags` | 问题-类目关联表 | 一条问题挂哪些类目，多维多选 |
| 7 | `attachments` | 附件表 | 截图与过程附件同表，强关联问题 |
| 8 | `replies` | 答复表 | 问题下面的一轮轮讨论，只增不改不删 |
| 9 | `project_sections` | 项目说明表 | 概况 + 各专业设计说明（成段 Markdown） |
| 10 | `project_metrics` | 经济技术指标表 | 一行一个指标 |
| 11 | `audit_log` | 操作留痕表 | 谁在什么时候把哪个字段从什么改成什么 |
| 12 | `idempotency_key` | 幂等键表 | 批量写入防重复（重试不会建两条） |
| 13 | `model_files` | BIM 模型文件表 | IFC 模型记录，一个项目同时只有一套（覆盖式） |
| 14 | `api_token` | 个人令牌表 | 一枚令牌 = 一个人的身份，只存哈希 |

```
projects（根，一切按项目隔离）
  ├─ project_members  谁在这个项目里、担任什么
  ├─ tags             这个项目的 41 项分类
  ├─ project_sections 这个项目的文字
  ├─ project_metrics  这个项目的数字
  ├─ model_files      这套项目的模型
  └─ issues（核心）
        ├─ issue_tags    挂到哪些类目
        ├─ replies       一轮轮讨论
        └─ attachments   截图 / 过程附件（可再挂到某条答复下）

users ── 贯穿所有表（创建人 / 执行人 / 上传人 / 操作主体，含 AI）
      └ api_token（一人一枚）
audit_log + idempotency_key ── 兜住「全量留痕」与「批量写入防重」
```

## 📐 通用约定（14 张表一起遵守）

| 约定 | 内容 | 为什么 |
|---|---|---|
| 主键 | 全库统一 26 位 **ULID** | 时间有序、跨库搬家不用重编号、外部没法靠 ID 枚举数据量 |
| 表名 | 一律复数 | 免得单复数两张皮 |
| 列名 | 库里蛇形、代码里驼峰，由定义里显式写列名对齐 | 同名两套写法是刻意的，靠定义绑住 |
| 枚举 | 字符串列 + 检查约束，**不用数据库原生 ENUM** | 换库不用改结构；加一个取值只改代码常量，不用发迁移 |
| 时间 | 库里存 **UTC**（SQLite ISO8601 串 / MySQL 带毫秒日期时间），**读写一律过 `server/database/time.ts`** | 两库存储形态不同，转换不收敛到一处就会静默拿到不同形状的值 |
| 软删 | 需要可回溯的表用一列「删除时间」（空 = 未删） | 与全量留痕一致，也兜住批量误删 |
| 跨项目防护 | 子表**冗余存项目 ID**，并让它**参与复合外键** | 项目数据物理隔离是判据 —— **数据库自己拦，不靠代码记得查** |
| 字符集 | MySQL 侧 utf8mb4 + 默认排序规则、InnoDB | 中文与 emoji |
| 改表方式 | 定义 → 生成迁移 → 应用，**禁手改表**（见文末「迁移与对拍」） | 多人同库的底线 |
| 库的边界 | 只建在本项目的库内，同一实例上别的库一律不碰 | 运维红线 |

**「看起来多余」的那三组唯一索引**：外键指向的列必须有唯一索引，所以这三张表各带一个纯为复合外键服务的索引，**删掉就等于拆掉跨项目防护**：

| 表 | 索引 | 供谁指向 |
|---|---|---|
| `issues` | `(id, project_id)` 唯一 | `issue_tags` / `attachments` / `replies` |
| `tags` | `(id, project_id)` 唯一 | `issue_tags` |
| `replies` | `(id, issue_id)` 唯一 | `attachments` |

`id` 本身已是主键，这组索引不加速任何查询 —— 它存在的唯一理由，是让「甲项目的问题挂乙项目的类目」这种写入在库层直接失败。

## 🔍 逐表要点

### `users` 用户表

- **AI 也占一行**：没有登录名、没有口令哈希、不加入任何项目，显示名固定「AI 助手」，只能借人的令牌被记为「代执行」；
- `subject_type` 区分 `human` / `ai`；`role` 是**平台级**角色（`platform_admin` / `user`），项目内角色不在这张表；
- `status` 停用 / 启用：离职或误建**只停用、不删号** —— 删了会连坐他提的问题与答复；
- `password_hash`：Node 内置 `crypto.scrypt` 加盐哈希（bcrypt / argon2 是原生模块，违反依赖纪律），任何地方不存明文；
- `avatar` 存文件名，图片本体在盘上；接口不回路径，只回「有没有头像」；
- `current_project_id` 为空时兜底取第一个参与项目，零项目账号进全站空态页；这一列**刻意不设外键** —— 它指 `projects`，而 `projects.created_by` 又指回 `users`，互设成环，改由服务端校验成员资格；
- `last_login_at` 供排查「多久没登录」；
- **账号那四个问题的落点**：注册 = 无自助注册（只有平台管理员建号，一个 `role` 就够）；找回密码 = 管理员重置 + 本人改密（覆写哈希即可，不需要新列）；**表里没有邮箱列**，邮件自助找回没有落点，要做须先加列；是否实名 / 登录失败锁定 / 验证码 —— 一个字段都没加，定了再补。

### `projects` 项目表

- `code` 对外编号：**系统生成**（年份 + 三位年内序号，如 `2026-001`），不可改、不接受客户端传入 —— 它是导入对账的锚点；与问题的展示编号是两回事，别混；
- `status` 只有 `active` / `archived` 两值。⚠️ **`archived` 在这里表达的是「已冻结」，不是「已归档」**：由平台管理员用 12.6 那一条端点切（只有那条路能切，它自己不在闸内，所以**冻结中的项目也能被恢复**）；冻结 = 成员侧写操作全关，拦的位置不是各端点而是所有写接口的集中闸；**两条例外**照做 —— 导出那一族（归档的目的就是以后还要查）与负责人改派这类平台管理动作；同值再切一次回「无变化」，不写库不留痕；
- `issue_seq` 取号计数器：新建问题在**同一事务内 +1** 取号，杜绝「查最大值再加一」的并发竞态；
- `settings` 是 JSON 文本：当前是 `ai_actions` 那份白名单（**逐项放开**），将来的项目杂项参数也进这里。⚠️ 一句容易踩空：**「默认全给」只对新建或从未保存过设置的项目成立** —— 负责人保存过一次，库里存的就是当时勾的显式清单，之后平台新增的动作对它默认是**关**的；
- 没有「一句话简介」字段（列表有名称 + 编号 + 封面足够）；概况、设计说明、指标各自成表。

### `project_members` 项目成员表

- 复合主键 `(project_id, user_id)` 天然防重复加入；`added_by` 记谁把他加进来的；
- `removed_at` 软移出（不删行）：**移出后重新加入 = 复用原行**、清空移出时间；`joined_at` 是首次加入时间，**复入不刷新**；
- `role` 六种取值：`project_owner` / `civil_lead` / `mep_lead` / `engineer` / `client` / `collaborator`。土建与机电专业负责人**权限完全相等是有意设定**（拆分只为称谓与归属），鉴权归并为单一「负责人能力组」—— 谁在这张表里给两者写出不同权限行，就是加了一条没拍过的口径；
- 专业负责人**可任命 / 降级同行**（与负责人同权，仅不能动 `project_owner` 那一行 —— 移交走平台管理员的独立端点）；
- **这张表不含 `ai`**：AI 是执行器，不是项目成员。

### `tags` 分类类目表

- **分类按项目独立**：同名类目在不同项目是两条记录，改 A 不动 B；
- `dimension` 四维：`type` / `major` / `special` / `subitem`；`name` **含前缀**（如 `专项-净高`，前缀是名称的一部分）；`code` 两位编号但**类型维度不编号**；`color` 四维各一色；
- **缩写唯一性是「维度内唯一」**：`UNIQUE(project_id, dimension, abbr)` —— 这不是笔误：标准清单里同一枚字母缩写同时是「专业-景观」和「专项-净高」，写成项目内唯一会在初始化那 41 项时直接撞车。还有一条例外：「专项-消火栓」的缩写就是中文那三个字；
- 41 项标准分类（类型 3 + 专业 9 + 专项 26 + 子项 3）由 `server/database/standard-tags.ts` 定义（**代码里仅此一份**），建项目时在事务内幂等灌入；`pnpm db:seed-tags` 给漏灌的项目补缺（只补、不改、不删）；
- **界面上「所有问题」那一档不入表** —— 它是「不筛选」那颗按钮，前端硬编码，所以展示口径是 42、表里是 41；
- **不建的列**：分组（维度可推导）、停用标记 —— 类目没有「停用」开关，**不能删，只能改名复用或留着不用**；历史问题挂着的引用不断，删除会让那些记录指向不存在的东西。

### `issues` 问题表（核心）

- `number` 展示编号 `VARCHAR(4)`，项目内 `0001` 起、与项目联合唯一；**不复用** —— 删了留空号，号只增不减；**上限 9999，超过必须显式报错**，不许静默截断或回绕（那会让两条问题共用一个号）；不可当主键用；
- `description` **六要素原文整段存文本**（不拆列）；只有 `drawing_version`（图纸版本日期）和 `grid_location`（轴网定位）拆成独立列 —— **图纸版本为空 = 「缺位置」**，是每日巡检的目标；轴网空了不算缺；
- `priority` 整数 1–4；`status` `open` / `closed`；
- `source`（`human` / `ai` / `import`）指**这条数据是谁写的**：由通道决定、不由客户端传；**出身列只在新建那一支定，之后谁改都不翻**；
- `executor_id` 执行人：**只有他能关闭 / 重开**；新建时默认 = 创建人；为空仅见于导入数据，由负责人补指派；
- `created_at` 写入后永不变；`updated_at` **任何改动都更新 —— 包括新增答复**（否则列表看不出有人回过）；`closed_at` 用于关闭率与处理时长；
- 分类不进这张表（走关联表），附件与答复也不（一对多各一张表）；索引：项目 + 状态 + 删除时间、项目 + 重要程度、执行人。

### `issue_tags` 问题-类目关联表

- 主键 `(issue_id, tag_id)` 防同一问题重复挂同一类目；
- `project_id` 是冗余列，**唯一作用是参与两条复合外键 —— 别删它**：问题必须属于本项目、类目也必须属于本项目，「甲项目的问题 + 乙项目的类目」这种组合数据库直接拒绝写入，不管是谁写的、是不是批量灌的；
- ⚠️ **维度全部可多选（含「类型」）⇒ 一条问题会同时出现在多个类目的计数里**：「各维度计数之和大于问题总数」是多选分类的**固有属性、不是数据错误**，报表必须显式标注这一句；连带地，业务规则里「先判类型」那条从数据库约束降级为 AI 判定建议。

### `attachments` 附件表

- **一张表管所有文件**：`category` 分 `shot` 截图 / `attach` 过程附件，处理路径完全不同（压缩转 WebP + 缩略图 vs 原样存只下载）。旧设计里「缩略图」曾是第三种取值，**已废**；
- ⚠️ **判「是不是截图」看类别列，不看 MIME 的 `image/` 前缀** —— 图纸类文件的注册类型本身就常以 `image/` 开头，按前缀判会误判；
- `issue_id` **非空** —— 附件是问题讨论中形成的结论与依据，问题没了它也没意义；`reply_id` 可空：建问题时贴的图留空，答复里贴的图填对应答复（「第一次传 A 方案、第二次传 B 方案」才分得清）；
- `mime` **不信任客户端报的类型**，须与文件头魔数比对；`original_name` 过程附件必需、截图按设计可空（下载时回响应头还原原名）；
- `file_hash`（SHA256）只作**完整性校验与孤儿比对，不承担去重** —— 文件名 = 记录 ID，同一张图重复上传得到两条记录；
- `storage_path` 存相对路径、不存二进制；**缩略图不入库**（目录 `issues/` 换 `thumbs/`、文件名同记录 ID 推导），表行数省一半；
- **问题软删时附件一并软删，磁盘文件一律不物理删除**（回溯优先）。

### `replies` 答复表

- **只增不改不删** —— 所以不加 `updated_at`、不加 `deleted_at`，也**不记 `source`**（说错了再发一条更正；主体归属由留痕表兜）；
- `user_id` 可以是 AI 账户；
- 连带好处：附件的答复外键**永远不会指向一条已删答复**。

### `project_sections` 项目说明表

- `section_type`：`overview` 概况 / `design` 设计说明 —— 将来加「绿色建筑」这类板块**不改表**，加一个检查值即可；
- 唯一约束 = `(project_id, section_type, discipline)`：一个项目的概况只有一条、结构设计说明也只有一条；
- ⚠️ **非专业板块（概况）的专业存空字符串，不是空值**：两种库的唯一约束都**允许多个 NULL 并存** —— 用 NULL，「概况」能被插进第二条，约束形同虚设；
- **专业不设外键**：设计说明本质是文档、不参与问题统计筛选，挂外键会让「删类目」的规则再多一处依赖，不划算；
- `title` 可空（界面用「板块 + 专业」拼出来）；`content` 是 Markdown（结构清晰、人机都好读，以后大概率是 AI 写的）；`source` 出身列同样建那支定、之后不翻。

### `project_metrics` 经济技术指标表

- 一行一指标：`group_name` 分组（用地与面积 / 规划指标 / 停车…）、`value` **纯文本原样录入**（能存 `≥35%`、`约 12000`）、`unit` 可空、`level` 0 主指标 / 1 「其中：」子项、`sort`、`note`；
- **拆行的规矩**：量纲不同的两件事各拆一行 —— 「建筑高度」和「层数」两行、「室外停车位」和「室内停车位」两行，塞一格以后没法比较；
- **为什么单独成表而不塞进项目表**：指标项会变，塞进项目表等于每来一个新指标就改一次表；而且「一行一指标」才能排序、带单位、**让 AI 逐项读写**（「把总建筑面积改成 12.8 万」），将来还能出跨项目对比；
- ⚠️ **这张表没有软删列**：删一行就是物理删、不可回滚 —— 这正是 AI 通道上那条删除降级（回「待删清单」、一行不动）**不是装饰**的原因。

### `audit_log` 操作留痕表

三个身份字段是全库最关键的设计：

| 字段 | 含义 | 判「谁做的」 | 判权限 | 人自己操作 | AI 代执行 |
|---|---|---|---|---|---|
| `actor_id` | **实际操作者**（谁的手真的动了数据），永远有值 | **看它** | 不看 | 人 | AI |
| `commander_id` | **发令人**（谁的权限生效） | 不看 | **看它** | **空** | 人 |
| `agent_id` | 代理执行的 AI | 不看 | **绝不参与权限判定** | 空 | AI |

读法：**「谁做的」看操作者；「谁的权限生效」看发令人，发令人空着就看操作者自己的角色。**

- `project_id` **可空** —— 平台级操作（建项目、开账号）不属于任何项目；
- `channel`（`web` / `api` / `ai`）指**这次操作走哪条通道**，与三张业务表的 `source`（这条数据是谁写的）是两回事；
- `target_type` **十种**：问题 / 答复 / 附件 / 类目 / 成员 / 项目 / 指标 / 板块 / 模型 / **账号**。⚠️ **这一列没有 CHECK 约束**，取值集合靠代码与文档对齐 —— 旧口径只列了九种、漏的正是「账号」那第十种（`member` 是某个项目里的成员关系、点得进项目设置；`user` 是平台账号本身，改状态改口令，没有可跳的项目页 —— 两件事不是一个东西）；
- `action`：`create` / `update` / `delete` / `restore`；
- **记录范围只记数据改动，不记登录与查看**（后者量极大，且「谁能看什么」是另一件事）；
- `changes` 用一列 JSON（字段 + 改前 + 改后），**只记真变化的字段**（diff 为空不落行）—— 三种库都支持按 JSON 路径查，「不能按字段筛」的劣势不成立。两条「为什么不那么存」：**长正文列不进明文**（整篇正文只记 `{changed, lengthBefore, lengthAfter}` —— 留痕的语义是「谁在什么时候动了哪一栏」，不是「动成了什么内容」；要正文对比该另开版本表，本期不建）；**外键值库里只存 ID、出接口才翻成人**（执行人改了名，历史自动跟着变 —— 留痕记的是主语不是快照；代价是表里新老两种形态并存，读的人两条都得留）；
- 四个索引分别服务：按对象回溯、按操作者、按发令人、按项目。

### `idempotency_key` 幂等键表

它解决的问题：批量写 50 条，网络一抖，第 30 条不知道写进去没有，于是重发 —— 结果变成两条。这张表让同一个键 + 同一份内容再来一次时**直接返回第一次的结果、不再写第二遍**（重放能拿到完全一样的响应，含新建记录的编号）。

- **唯一约束 = `(actor_id, key)`，挂在实际操作者而不是发令人上** —— 这不是口味：发令人可能为空（人自己调用时留空），而**空值不受唯一约束约束**，挂上去就是漏洞；不同调用方各自用同一串互不干扰；
- `request_hash`（SHA256 指纹）+ 首次响应的状态码与内容都存：重放且指纹相同 → 原样返回；**同键不同内容 → 409 拒绝**（防止键被误用去写别的东西）；
- **预览（`dryRun`）不落这张表**，而且这不是图省事：预览与真跑是同一人同键的**两步**（一次带 `dryRun` 一次不带，指纹自然不同），预览若参与判定，「先预览再真跑」这个正常用法会**必然**撞上那条本只防误重放的 409；
- 默认 24 小时过期清理，表不无限膨胀；⚠️ `key` 是 SQL 保留字，手写查询要加引号。

### `model_files` BIM 模型文件表

- **一个项目同时只有一套模型**：重传 = 覆盖式整套替换。`version` 这一列**恒为 1** —— 字段留着，是万一回到多版本时不必再迁移；既然同时只有一套，也就不存在「哪条版本线」要分辨；
- **没有软删列 = 硬删**：这是「业务文件不物理删除」红线被合法破例的三处之一（导出产物、上传半成品、模型与解析产物），判据是覆盖式形态决定的 —— 旧那套不让位，磁盘就翻倍。删除顺序**先新后旧**：新那套落库并起解析之后才删旧文件，中途失败不会出现「模型没了」的空窗；
- `original_name` **不只是展示用**：转换器判专业靠的就是它的**前缀**（`A_` 建筑 / `S_` 结构…）。这条链路的连带纪律：**盘上的名字不可读**（`storage_path` 文件名 = 记录 ID，防穿越 + 覆盖式好定位），「拿平台下载的副本回灌」会让前缀消失、全套快照 0 行而状态照样「成功」——**重传一律用原始图纸目录里的文件**；
- **这张表里没有任何解析状态、也没有任何快照数据**。解析产物住在另一棵树里，不属于这 14 张表：模型本体 `models/<记录ID>.ifc` · **解析库** `parse/ifc-<项目编号>.db`（基础表 + 每张快照一张表，**张数是浮动的** —— 机电那套口径还没整理完，任何判断不许按当前张数写死；画像的数据源在这里）· **状态旁文件**（解析四态与快照张数 —— 为什么不入库：解析是后台进程，状态每几秒变一次，写进主库就是把外部进程的进度塞进业务事务）· **改名名单**（盘上名 → 原始名；**跑转换器必须带上它**，没有它快照全算 0 行而状态还写着成功）。

### `api_token` 个人令牌表

- `token_hash` UNIQUE（SHA256）—— **库里永不存明文**，明文只在生成那一刻展示一次；
- **一人一枚**：令牌只回答「是谁」，**不携带任何权限** —— 每次请求按成员表现查项目内角色，角色一变立即生效；**重置 = 删旧插新、旧的立刻失效**，不做并存；
- **长期有效：这个平台没有「有效期」这个概念**，令牌不会过一阵自己失效；本期不做限流；
- 通道定性 = **仅 MCP**：它的一切直连 REST 调用（读写皆然）一律被拒，人查数据用网页；
- `last_used_at` 是高频写入列，做了**节流**（60 秒内不重复写）且**写失败不影响请求** —— 一次记账不该把正常调用打成失败；
- ⚠️ `revoked_at` 这一列**当前没有任何端点写入**（重置与吊销都是删行）。留着它是因为凭据层那条查询只按哈希命中，这一列是「带吊销标记的行」**唯一的闸**（手工改库、或将来真做软吊销时被吊销的令牌照样拦得住）—— 不许顺手删。附带效果：契约里那枚「令牌已吊销」的错误码今天发不出来。

## 🚫 不建的表（及理由）

| 不建 | 理由 |
|---|---|
| 会话表 | 登录态用加密封装的 Cookie（`nuxt-auth-utils`），不需要服务端会话 |
| 通知表 | 站内通知不做 —— 要看别人改了什么，去操作记录那一页翻，不建第二套「消息中心」心智 |
| 登录失败 / 锁定表 | 失败锁定与验证码**尚未定案**，定了再补 |
| 问题参与人表 | 不建：一般没什么用。连带影响 —— 报表按「创建人 / 执行人」口径，不是「按人员贡献」 |
| 导出任务表 | 不建：带图导出是进程内后台任务 + 流式写盘，产物直接落盘、按目录当任务 ID；过期清理由**启动清扫**做 —— 代价是「重启即失效」，也正因如此启动清扫才有强判据 |

## 📦 文件在哪里落盘（表管不到的那一半）

库里只存元信息，**图片与模型不进库**。目录根由开关可改，默认在 `data/` 下：

```
data/uploads/<项目ID>/
  ├─ issues/<记录ID>.webp      截图（兜底转 WebP 后存）
  ├─ thumbs/<记录ID>.webp      缩略图（不入库，按记录 ID 推导）
  ├─ attach/<记录ID>.<扩展名>   过程附件（原样存、不压缩不转码）
  ├─ cover/<项目ID>.<扩展名>    项目封面（文件名是项目 ID，单张替换即覆盖）
  ├─ models/<记录ID>.ifc       模型本体
  └─ parse/                    解析库 + 状态旁文件 + 改名名单
data/uploads/avatars/<用户ID>.<扩展名>   头像（用户级，在 uploads 之内、不带项目 ID）
data/uploads/.incoming/<项目ID>/<批次ID>/  上传暂存区（半截文件的家）
data/exports/<项目ID>/日期-时间[-序号]/     导出产物（只有这一族才有日期目录）
```

⚠️ `issues/` 与 `attach/` 底下**没有日期层** —— 目录只到「项目 / 类别」为止，文件名就是记录 ID；带日期时间目录的只有导出产物那一族，别记混。

四条硬规矩：

- 落盘目录**绝不明文静态暴露**，下载一律带「作为附件」的响应头（防上传一个 HTML 存成 XSS）；
- 类型白名单 + **扩展名与文件头魔数双重校验**；
- **先落盘、再写库**，写库失败删掉刚落的文件 —— 反过来会留下「库里有记录、磁盘没文件」的坏数据；
- **业务文件一律不物理删除**，例外只有三处：导出产物、`.incoming/` 半成品、IFC 模型与它的解析产物（别把第三条例外推广到问题 / 附件 / 头像）。

尺寸闸一览（**模型与附件是两套闸，别互相引用**）：过程附件单件 10 MB、单次不超过 6 个 · 头像 5 MB · 模型单件 200 MB、单次不超过 60 个、**一整套合计 8 GB**。

## 🔄 迁移与对拍

四份表定义同时存在，靠一条命令对拍：

| 定义 | 文件 | 地位 |
|---|---|---|
| SQLite 版 | `server/database/schema.ts` | **唯一真源** |
| MySQL 版 | `server/database/schema.mysql.ts` | 方言内部件，须与真源同形 |
| 手写建库 SQL | `scripts/db/01_schema_sqlite.sql` · `01_schema_mysql.sql` | 建库用，同样要跟着改 |

- **业务代码不许直接 import 上面任何一份**，只从 `server/database/tables.ts` 取表 —— 它按当前连的库挑方言，两边列名约束完全一致；
- 流程四步：改 `schema.ts` → `pnpm db:generate`（SQLite）与 `pnpm db:generate:mysql`（MySQL）→ `pnpm db:migrate` 应用 → **`pnpm db:check` 对拍**。`db:check` 逐项比 14 张表、136 个列、35 个索引名、31 个外键名、16 个检查约束名 —— **这才是防漂移的真闸**；
- `db:check` 用文本解析读 schema，对写法敏感 —— 已知踩点：索引回调 `(t) => [...]` 若被改写成别的形式，索引会被静默漏读（表现为「整表索引凭空消失」）；
- MySQL 库重建须先手工 DROP 全部表再跑（建表语句全是 `CREATE TABLE IF NOT EXISTS`，改 DDL 对着已存在的表不会生效，症状是不报错但对拍数出旧值）；
- `pnpm db:check` 之外，改完任何表定义后库的实况以库为准，别照文档记载的条数对账。
