## 二、项目深度评估

**规模定位**：约 2.6 万行属于**中小型全栈项目**（参照系：个人小项目 < 5 千行；中型开源库 1~5 万行；平台级系统 10 万行以上），约相当于传统模式下 2~3 人干 1~2 个月的量。

**深度定位**：**「精品级 MVP」** —— 比玩具 demo 深得多，离平台级系统还有明确差距。

做得深的部分（超过同体量项目平均水准）：

1. **权限与审计模型是全项目最深的部分** —— 双层角色（平台 / 项目内）、AI 代理执行的三身份分离（实际操作者 / 发令人 / 代理 AI）、鉴权七步固定顺序、AI 动作清单二次过滤、子表复合外键在数据库层拦截跨项目越权。这套闭环很多成熟商业系统都做不清楚。
2. **接口规范** —— 43 个错误码、幂等键、dry-run 预演、批量部分成功语义、统一错误信封、「按 code 不按 message 判分支」。
3. **工程纪律** —— 四份表定义程序化对拍、双方言迁移、本地 git 钩子门禁、禁用字符自检。
4. **多数据库是真验证过的** —— SQLite / MySQL 双方言从开发第一天并行跑，不是「理论上支持」。

明确短板：

1. **零自动化测试**（见 1.4）—— 回归全靠人工手测，是「能开源」与「可持续维护」之间最实质的差距；
2. **领域复杂度有限** —— 业务本质是「带权限的问题台账」，深度主要体现在横切面（权限 / 审计 / 接口）而非领域建模。

一句话：**架构判断力和工程纪律明显高于代码体量的全栈应用；权限设计、接口契约、文档配套是中型团队水准，测试覆盖是个人项目水准。**

### 第二档 · 工程质量：补自动化测试（最大单项）

### 第五档 · 规模上来之后（现在不急）

1. `keyword` 筛选是 LIKE 全扫 —— 十万条级建议上 FTS5 / FULLTEXT（设计文档早预留了这个抽象点）；
2. 4.1 列表返回 `description` 全文 —— 万级数据响应变重，契约已预留 `summary` 字段；
3. **`idempotency_key` 没有定时清理任务**（已核实：过期行只靠「读时惰性失效」，`server/utils/idempotency.ts:74`）—— 表会无限增长，补个定时清理即可；
4. 导出任务是进程内的：PM2 cluster / 多实例部署会坏，单机没事 —— 至少在部署文档写明这个约束；
5. `audit_log` 无限增长，无归档 / 保留策略。

## 四、结语

这个项目最难得的不是功能量，而是**决策质量**：几乎每个「看起来奇怪」的实现背后都有一条记录完整的取舍理由（见 [设计决策记录](/design/decisions)），这在同体量的项目里非常少见。若补上第二档的测试层，它就是一个完成度相当高、可以放心交给陌生贡献者的开源项目。
